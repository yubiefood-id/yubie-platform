Primary official references; verify their latest live revisions and obtain official support confirmation where documents are insufficient:

- Transaction History: https://docs.ipaymu.com/id/docs/transaction/history-transaction
- Sandbox onboarding: https://sandbox.ipaymu.com/register

The documented `POST /api/v2/payment` creates a hosted redirect and returns `Data.SessionID` and `Data.Url`; `POST /api/v2/transaction` expects a `transactionId`, not a SessionID. Do NOT invent cancel-by-session endpoints or an undocumented provider idempotency guarantee. Explore `POST /api/v2/history` and callback fields (`sid`, `trx_id`, `reference_id`, `merchant`), but prove an authoritative, bounded, unambiguous recovery path for a newly-created session under timeout and provider 5xx. Ask provider support for explicit session cancellation, lookup by reference, duplicate-reference behavior, and transaction-ID discovery. Record citations, signed-off provider answers, and sandbox evidence in `IPAYMU_PROVIDER_CONTRACT.md`.

Use API request HMAC-SHA256 over the **exact bytes of the JSON body sent** per current docs, with appropriate method, VA, hashed body and API key. Compare test vectors with official examples. Callback signature is a DIFFERENT algorithm: canonical normalization and sort of callback fields with HMAC keyed by merchant VA as specified; support x-www-form-urlencoded and JSON if configured, verify timestamp/replay context where documented, constant-time compare, body limit, content-type checks and merchant+reference+amount+currency+session/transaction mapping. Never promote payment from unverified browser redirect or solely a claimed webhook status.

Hard stop for enabling iPaymu sandbox on actual staging: missing merchant sandbox credentials, undocumented session-to-transaction reconciliation, unsupported session cancellation with no safe fail-closed alternative, unverified callback fixtures, or missing durable storage/worker.
